# GKE Autopilot Migration Decision Record
**Date:** Session BP (June 13, 2026)  
**Decision:** Migrate from Standard GKE (us-east1) + L4 GPU pool → GKE Autopilot (us-central1) + T4 GPU  
**Status:** APPROVED — awaiting execution

---

## Why migrate

### The billing-leak class of problems is structurally fixed by Autopilot

Standard GKE has a fatal operational gap: scaling a Deployment to 0 replicas does NOT remove the underlying VM. The Session BO incident demonstrated this: 3 × g2-standard-8 L4 nodes ran at $3.27/hr because the node-pool resize and the deployment-scale are two separate GKE operations. The fix we applied (gpu-start/stop scripts that resize the pool) works, but it can still fail (RECONCILING state, zone mismatch) and requires the operator to remember to pair gpu-stop with every gpu-start.

On Autopilot, **this class of problem does not exist.** Autopilot bills per running pod's resource request. Scale Ollama to 0 → no pod requests a GPU → no GPU node exists → zero GPU billing. The VM lifecycle is managed by Autopilot automatically.

### Why T4, not L4

The current Gemma workload is **short-form generation only:**
- `_gemma_extract_findings`: 80 output tokens (structured JSON extraction from retrieved docs)
- `agent_chat`: 200 output tokens (RAG-grounded conversational answer)
- Advisory prose / streaming: 100–150 output tokens

Max output: 200 tokens. Single-user. No batching. The VRAM-fit constraint is the only sizing factor.

| Model | VRAM footprint | Fits T4 (16GB)? |
|---|---|---|
| gemma4:latest (~6GB, actual default) | ~6GB | ✅ 10GB to spare |
| gemma3:12b (upgrade path if needed) | ~8GB | ✅ comfortable |
| gemma:27b (stale ollama.yaml header, never actually pulled) | ~17GB | ❌ |

L4 was sized for a Gemma generation role that no longer exists (live document generation, long-form inference). That role was incrementally replaced by scripted scenario documents (Session BJ). The L4's 24GB has been idle headroom since then.

**T4 at ~$0.35/hr vs L4 at $1.09/hr — 3× cost reduction per showcase hour, with T4's broader regional availability eliminating the us-east1 zone-quota friction that caused Session BO.**

## What migrates (the full picture)

### Migrates easily (manifest-level)
- All `gke/**/k8s/*.yaml` manifest files — applied to the new cluster
- Secrets — re-generated by `start-alloydb-omni.sh` and `start-rabbitmq.sh`
- Application images — already in Artifact Registry `us-central1-docker.pkg.dev/gdc-pm-v2/gdc-models/`

### Re-seeded (not migrated from PVC)
- **AlloyDB data** — do NOT attempt to migrate the PD. Re-seed:
  - `init-schema.yaml` runs automatically via `start-alloydb-omni.sh`
  - H1/H2/H3 RAG documents seed automatically via 5 app.py background threads (no manual script)
  - OEM manuals optionally re-ingested via `scripts/ingest_manuals.py`
- **ollama-models PVC** — re-pull gemma4 (~6GB, ~5–15 min first GPU start). Model is cached on PVC; subsequent starts skip the pull.

### Discarded (no longer needed)
- Standard GKE `gpu-pool` node pool (Standard GKE concept — Autopilot has no user node pools)
- Node-pool resize logic in `gpu-start.sh` / `gpu-stop.sh`
- `terraform/gke.tf` gpu_pool and default_pool resources (barred from apply anyway)

## Pre-flight verifications (run before teardown)

1. **T4 availability in us-central1:** `gcloud compute accelerator-types list --filter="zone:us-central1* AND name=nvidia-tesla-t4"`  
   Expected: multiple zones (us-central1-a, b, c) all showing T4.

2. **AlloyDB Omni Autopilot compat:** AlloyDB Omni is a standard Deployment (single container, no privileged/hostPath, RWO PVC). Autopilot's security policy permits this pattern. No known blocker.

3. **Workload Identity confirmation:** The `--workload-pool` flag on cluster create enables it. The inference-api's Workload Identity binding to GCS (model artifacts) must be re-applied post-cluster-create if used. (Currently models are baked into the Docker image, so this may be a no-op.)

## Teardown sequence (live cluster destruction)

> **Do this only when ready to lose the current cluster and rebuild.** All live dev state (rag_documents, field_intel) is lost; re-seeding recovers it automatically.

```bash
# 1. Verify Ollama is scaled to 0 (no GPU billing)
kubectl get deployment ollama -n gdc-pm -o jsonpath='{.spec.replicas}'
# Expected: 0

# 2. Verify no GPU nodes exist
kubectl get nodes -l cloud.google.com/gke-accelerator=nvidia-l4 --no-headers | wc -l
# Expected: 0

# 3. Delete the current Standard GKE cluster
gcloud container clusters delete gdc-edge-simulation \
  --region us-east1 \
  --project gdc-pm-v2 \
  --quiet

# 4. Follow deploy-from-scratch.md from Step 0
```

## Cost comparison

| Item | Standard GKE (current) | Autopilot + T4 (target) |
|---|---|---|
| Cluster management fee | ~$73/mo | ~$73/mo (same) |
| CPU nodes (e2-standard-4, 24/7) | ~$97/mo | Pay per pod request (~$95–130/mo estimate) |
| GPU idle risk | **Non-zero** (billing continues if resize forgotten) | **Zero** (Autopilot auto-scales to 0) |
| GPU active cost | $1.09/hr (L4) | **$0.35/hr (T4) — 3× cheaper** |
| Zone availability | us-east1-b only (quota friction) | us-central1 multi-zone (T4 widely available) |

**The primary win is risk elimination, not hourly rate.** One forgotten weekend of 3×L4 = ~$235. Autopilot makes that impossible.
